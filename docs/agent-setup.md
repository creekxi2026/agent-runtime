# 为用户配置 Agent Runtime

本文件供**已有、能够执行部署操作的 Agent**读取并遵循。用户可以说：

> 阅读 agent-runtime 仓库中的 docs/agent-setup.md，帮我配置一个运行环境。

无需注册、下载到技能目录或安装本文件，也无需向新实例注入首聊钩子。部署完成并交付结果后结束本次流程，保留仓库指引供下次使用。读取仓库不代表用户已批准安装。

## 1. 按顺序了解需求

先读同一版本的 [README.zh-CN.md](../README.zh-CN.md)、[compose.yaml](../compose.yaml) 和 [runtime.env.example](../runtime.env.example)，确认现有镜像、默认工具和配置契约。不要根据过往机器的目录、账号或网络设置推断本次配置。

向用户询问下面的信息；已在当前对话明确提供的直接复用，不再重复提问：

1. **实例叫什么，给谁使用？** 用户名可用于建议实例名，例如 `user01` → `agent-user01`。区分实例名和镜像：默认使用现有 `ghcr.io/creekxi2026/agent-runtime:latest`，无需给每位用户构建或发布新镜像。
2. **主要拿来做什么？** 例如飞书办公、处理本地 Word/Excel/PDF、网页操作、数据分析或开发。了解输入、期望产物，以及是否需要浏览器/外部账号，不要求用户先列软件名。
3. **如何连接 Multica 和模型服务？** 用户可以提供自托管配置命令中的服务地址以及登录凭据来源；从中提取 API 地址、Web 应用地址和登录方式，不要求重复填写工作区 ID。登录后自动发现身份和工作区，沿用当前任务已明确的目标；只有多个目标仍有歧义时才询问。Multica 的 `mul_` 登录 token 与模型 API key 是两类凭据，不能混用。模型已有共享配置时，确认共享目录即可，无需重复提供 key。

用户已指定与现有实例同机时，先只读检查该实例的 Compose 工作目录及挂载，自动沿用已确认的部署根目录。统一布局建议为目标主机的 `$HOME/agent-runtime/<user>`：例如 `agent-user01` 对应 `user01` 子目录。不同实例使用独立 Compose 项目和 HOME；不要为统一布局自动迁移现有实例。只有主机或根目录仍不明确时才补问，不要默认把当前执行任务的机器当成目标主机。实际主机绝对路径不写入本仓库。

只在需要对应服务时补问飞书应用配置、用户授权、网络代理或存储挂载。密钥通过用户批准的私密配置方式提供，不要求贴入聊天、提交 Git，也不复制现有用户的 HOME、认证文件或整个环境变量集。

## 2. 调研并提出软件方案

读取镜像依赖说明；目标机器上已有对应镜像或实例时，使用只读检查核对实际工具与版本。尚未有镜像时，可依据仓库清单出方案，把运行时核验列入安装步骤，不为了做检查提前启动实例。

结合用途选择维护中的软件，核对官方安装说明、CPU 架构、Python/Node 版本、二进制包可用性及认证要求。下表是选择示例，不是必须全部安装的清单：

| 需求 | 优先利用 | 可能增装及边界 |
| --- | --- | --- |
| 飞书文档/云盘/表格 | 镜像中的 Lark CLI 和 skills | 通常先完成应用配置和本人授权，无需另一套办公软件 |
| 网页访问与操作 | Playwright CLI、Chromium | 先验证已有浏览器；特定登录由该用户完成 |
| CSV/JSON | Python 标准库 | 无需额外包 |
| 本地 Excel | Python | 可选 openpyxl；不等同于 Excel 公式重算/渲染 |
| 本地 Word | Python | 可选 python-docx；不保证完整排版渲染 |
| PDF | Python | 按读取/合并、生成、渲染、OCR 分别选择工具，不把它们视为同一能力 |
| 格式转换、演示文稿、数据分析 | 现有运行环境 | 依据具体任务选型，不默认装完整桌面或开发套件 |

增装的 Python 依赖优先放在私有 HOME 下的虚拟环境；用户 CLI 和数据也优先持久化在 HOME。不要修改系统 Python。若软件必须安装系统包，说明它们在容器重建后如何恢复，例如可复现的派生镜像；不要把容器可写层中的临时 apt 安装描述为持久部署。构建/发布派生镜像需要列入方案批准范围。

给用户一份具体的确认单：

```text
实例名 / 使用人：
部署目标 / 独立目录：
基础镜像 / 架构：
用途与验收样例：
已内置且直接复用的软件：
拟新增的软件、版本范围、安装理由与持久化方式：
Multica 服务 / 工作区 / 登录身份与方式（不含秘密）：
模型接入方式 / 凭据来源（不含秘密）：
用户授权步骤：
资源 / 存储 / 网络配置：
是否还需创建平台中的 Agent；如需，列出名称、职责、权限及 Runtime：
本次将执行的操作与完成标准：
```

默认可建议 2 CPU、4 GiB 内存及私有 HOME 命名卷；按用途调整。若“名字”明确指容器名，列出实例专用 `container_name` override；仅设置 `COMPOSE_PROJECT_NAME` 时 Compose 通常生成 `<instance-name>-runtime-1`，不要混为一谈。

**并发默认不额外覆盖。** 不自动设置 `MULTICA_DAEMON_MAX_CONCURRENT_TASKS=1`，创建 Agent 时也不主动收紧并发。若旧配置已设为 1，移除 daemon 的环境变量覆盖，并按当前 CLI 契约恢复 Agent 默认值。已核验的 Multica 0.6.1 中 Agent 默认并发为 6，字段只接受 1–50，没有无限制值；明确说明“恢复默认”与“无限制”的区别，不用 0 或 50 冒充无限制。

**等待用户确认这份方案，再执行安装、启动、授权变更或创建 Agent。** 现有确认已覆盖的操作直接继续。新增软件、权限或部署范围超出原确认时，只确认变化部分，不重复要求批准整个方案。

## 3. 执行已确认的部署

按 README 的快速开始和存储说明执行，保持配置来自同一仓库版本：

1. 检查目标主机 Docker/Compose、架构和资源；核对实例名、目录、容器及卷是否已存在。遇到同名资源先确认归属和复用意图，不覆盖或删除旧数据。
2. 在独立部署目录准备 Compose 文件与私有 `.env`。设置唯一 `COMPOSE_PROJECT_NAME`、镜像和资源，**先确定 HOME 存储与 `COMPOSE_FILE`，再登录**；存储变更不会自动迁移认证或数据。不要覆盖已有 `.env`。
3. 拉取已确认镜像，记录实际 digest。后续使用同一套 Compose 参数，以免认证、软件安装和守护进程落到不同的 HOME。
4. 完成模型认证。Multica 使用交互方式时先完成登录；使用 bootstrap token 时准备私密配置，由步骤 6 启动时应用。按下一节核对服务地址，登录完成后核对工作区。
5. 按确认的软件清单检查已有安装，只补缺失依赖。以容器应用用户 `1000:1000` 安装 HOME 内的软件，不把工具装到当前 Agent 的宿主机或临时任务环境。例如已批准的 Python 工具可安装到 `$HOME/.local/share/office/venv`；后续任务使用该环境的 Python。
6. 执行 `docker compose up -d`，检查实例状态和经过脱敏的日志。如需飞书或网页账号，由对应用户完成授权；缺少授权时明确列为未完成，不借用其他人的账号。
7. 仅当确认单包含创建平台 Agent 时，核对是否已存在，创建或绑定正确 Runtime 并配置批准的职责与调用权限。镜像内有 CLI，不代表已经创建了平台 Agent。

遇到无法解决的安装或认证错误时保留已完成步骤和数据，交付具体错误与剩余事项。不要把暂时失败变成重新安装整个环境或清空 HOME。

## 4. 连接并核验 Multica 工作区

| 参数 | 用途 |
| --- | --- |
| `MULTICA_SERVER_URL` | 自托管 API 地址；官方云按当前模板留空 |
| `MULTICA_APP_URL` | 自托管 Web 应用地址；与 API 地址分别核对 |
| 工作区名称/ID | 登录后在目标服务核对身份、成员资格和 Runtime 注册位置；不是本仓库现成的 `.env` 字段 |
| 登录方式 | 交互登录，或通过私密渠道配置的 `MULTICA_BOOTSTRAP_TOKEN` |
| 模型认证 | Codex 的用户登录或获准的 API 配置，独立于 Multica token |

自托管且使用交互登录时，必须**在第一次登录前，在新实例内**设置实际 `server_url` / `app_url`。README 给出的 `docker compose run --rm runtime multica config set ...` 命令用于此步骤。只填写 `.env` 的 URL 不会让交互登录自动使用这些地址；入口仅在启动守护进程时应用它们。

使用 bootstrap token 时，按入口契约由新实例启动时应用 token 和服务地址。不要将 token 放进仓库、日志、确认单或命令行实参；从批准的私密配置源传入。不要把当前任务的 Multica task token 当作用户登录 token。

### 已有共享模型配置

用户要求关联共享目录时，先核对现有部署的挂载或已知共享位置。**下载缓存目录不是模型认证目录。** 来源必须是已获准共享、包含可读 `config.toml` 和 API-key 模式 `auth.json` 的专用目录；没有找到时只询问具体路径，不猜测其他用户的私有 HOME，也不从旧备份或临时目录提取凭据。

复用仓库的 `compose.shared-codex.yaml`，把它加入该实例现有的 `COMPOSE_FILE`，保留已有 override，并设置 `SHARED_CODEX_DIR` 指向经过核验的来源。只读挂载由入口链接两个配置文件；会话和工作文件继续使用实例私有 HOME。不要挂载整个 `.codex`，也不要共享会刷新令牌的 OAuth 登录状态。检查配置时仅输出认证类型、文件是否存在等必要元数据，不打印密钥。

变更前确认该实例没有运行中的任务；Compose 校验后只重建目标实例。核验只读挂载、两个链接、真实模型调用及重建后持久化，不能以 `codex login status` 或 Runtime 在线代替真实任务成功。缺少共享来源路径时可准备 override 文件，但不启用无效挂载。

在**目标容器**中按其已安装版本的 `multica workspace --help`、`multica workspace list` 和 `multica workspace switch --help` 核对并选择默认工作区；再核对目标空间的 Runtime 在线状态。当前 CLI 登录会自动发现账号可访问的工作区，`workspace switch` 只改变默认工作区，**不构成“仅连接这个空间”的限制**。如果用户要求只供一个空间使用，应检查实际 Runtime 可见性和账号权限，不能仅凭默认工作区已切换就宣称隔离完成。

上述登录和配置针对新实例独立的用户配置。不得在执行本次任务的 Agent 环境中切换宿主机用户的 Multica profile、停止当前 daemon，或借用宿主机所有者凭据。

## 5. 验收、交付并结束

至少验证：容器稳定运行、目标 Multica 工作区看到正确 Runtime、一次真实模型任务成功，以及用户确认单中的代表性业务任务能完成。若承诺文件交付，验证用户确实能下载/打开结果；仅打印内部路径不算交付。承诺持久化的软件及文件需验证重建/重启路径，测试不得中断其他人的任务。

交付实例和使用入口、已装软件及版本、认证完成情况、测试结果、更新与停启方法、未完成事项。面向公开仓库的文档/提交仅使用示例值或参数名；实际主机地址、部署目录、用户身份和私有服务配置只保存在批准的部署记录中，秘密不进入交付文本。

完成后结束，不安装或删除引导 Skill，不改用户后续对话流程，不创建定时任务。将来新增能力时，重新按需求提出增量方案；不因再次读到本文件而重复安装。
