# Agent Runtime 部署经验

本记录来自一次办公实例的部署实践，用于改进后续开通。操作入口仍是 [agent-setup.md](agent-setup.md)，不需要安装引导 Skill。以下只记录可复用规则；真实账号、地址、宿主机路径和密钥保留在实例私有部署记录中。

## 先查，再问

本次绕路主要来自过早推断需求、重复追问可查信息，以及把容器、模型和平台登录混在一起判断。后续按下表处理：

| 情况 | 先做什么 | 何时才问用户 |
| --- | --- | --- |
| 用户说“与现有实例同机” | 读取该实例的 Compose 配置、工作目录标签和实际挂载；沿用确认的部署根目录 | 主机或目录仍有多个合理候选 |
| 用户说“已有共享配置” | 检查获准来源及文件类型；区分下载缓存和模型认证；已有 `.codex` 可只挂载两个文件 | 无法定位来源或共享授权未覆盖该来源 |
| 用户提供登录命令 | 提取服务地址和凭据用途，先设置自托管地址，再在新实例登录 | 有多个目标工作区且上下文未指定 |
| 用户将 token 称为“API key” | 按凭据类型和实际登录结果识别用途；Multica token 与模型 key 分开配置 | 另一类凭据确实缺失，且没有获准的现有配置 |
| 用户已确认方案 | 复用本次会话中的授权，执行已确认步骤 | 新增权限、费用或范围需要用户决定 |

有局部错误时先读脱敏错误信息。例如容器重启循环可能是 Multica 返回 `401`，不能仅凭刚修改过挂载就认定文件权限有问题。检查可读性与认证结果分别取证，不先放宽权限或重装。

## 选择足够的方案

- 单个办公用户可先用现有镜像，复用宿主机已有镜像层。镜像带有开发工具不意味着这些工具持续占用 CPU；是否另做 `office` 变体，应根据实际体积、部署规模和维护收益决定。
- 日常公文、讲话稿、函件和演示稿，可先用私有 HOME 中的 Python 虚拟环境，加 `python-docx`、`python-pptx`。格式转换、最终渲染、OCR 等另按需求补齐，不默认安装完整桌面套件。
- 根目录 `AGENTS.md` 指向一份操作指引即可。用户要的是让现有 Agent 执行开通流程，无需先设计首聊钩子、临时 Skill 和自删除机制。
- HOME、工作文件和会话独立；仅共享用户明确指定的模型配置。`compose.shared-codex-files.yaml` 可只读挂载已有 `.codex` 的两个文件，不暴露整个目录。
- 共享 API key 不适用于需要刷新写入的 OAuth 凭据。单文件 bind 在宿主机原子替换文件后需要重建容器；不能承诺密钥更新即时生效。

## 账号和并发必须明确

实例名、Multica 登录账号、工作区及 Agent 是不同对象。更换 token 可能换到另一账号和工作区；应在创建 Agent 前完成身份核对，避免先建在管理员空间再返工。迁移时重新读取 Runtime ID，不沿用旧空间 ID；只清理本次创建且确认无任务的旧测试入口。

daemon 总并发与单个 Agent 并发是两层配置。不要自行把办公实例设为 1。本次核验的 Multica 0.6.1 中，Agent 默认值为 6，接受 1–50；用户要求 50 时设置 50，但它仍是上限。daemon 未设覆盖表示采用自身默认值，不等于无限制，也不代表已验证 50 个任务能在给定 CPU/内存下同时运行。未来版本按实际 CLI 契约核对。

## 分别记录验收证据

| 验收项 | 能证明什么 | 不能代替什么 |
| --- | --- | --- |
| Compose 校验、容器运行、Runtime 在线 | 配置可解析，进程和平台连接正常 | 模型可用、平台聊天任务成功 |
| 新容器内真实模型调用 | 该容器的模型配置、认证和请求可用 | Multica 网页首聊及用户权限验收 |
| 模型内容导出 DOCX/PPTX，再重新打开 | 文档依赖可用、内容和基本结构正确 | Word/PowerPoint 最终视觉排版 |
| 重建容器后检查认证、依赖及文件校验和 | 数据与环境持久化有效 | 备份恢复或升级兼容性测试 |
| 附件交付 | 用户有获取文件的入口 | 用户已实际下载或打开 |

本次已完成真实模型调用、三份 Word 文稿及四页 PPT 的导出与读回、重建后的认证及文件保留，并通过平台附件交付。未测试 Office 最终视觉排版和网页端首聊；验收报告应保留这些边界，不能把工具测试夹具说成模型成果。

## 下次的最短流程

1. 读取指引，复用已知的实例名、用途和目标主机；只读核对现有部署及获准的共享来源。
2. 补齐真正缺少的登录信息，给出软件和部署清单；沿用已有批准。
3. 准备独立目录及 HOME，配置服务地址、模型来源和 Multica 登录，核对账号与工作区。
4. 持久安装所需工具，启动 Runtime，再创建或绑定 Agent，设置用户要求的权限及并发。
5. 验证真实模型、代表性业务文件、重建持久化及交付入口，报告实际通过与未测项目。
6. 更新通用指引和私有部署记录，交付使用入口、停启方法及更新注意事项，结束流程。

文档沉淀也要区分交付状态：本地提交或附件不等于远端仓库已更新。若只交付补丁，明确说明尚未推送；不要给远端尚不存在的文件链接，让下一位 Agent 误以为已经可读。
